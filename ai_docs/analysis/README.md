## Naive LLM

The naive-LLM experiment (`naive_llm_caruca/`, task 016): a general-purpose coding agent given only the
goal, the formats and four examples, with no method. It differs from the stage-by-stage rebuild above,
so documents under this heading stand alone and do not rely on the earlier findings: every claim cites
the paper, v1's code and files, or the naive-LLM runs' own logs. Per-run analyses live in each run's
`analysis/` folder.

| [`white_paper_addendum_naive_llm.md`](../../naive_llm_caruca/white_paper_addendum_naive_llm.md) | **Version 0.5, 26 October 2026, draft.** "In brief" (added in 0.5): a plain-language summary of the three main findings, with one diagram (`naive_llm_caruca/diagrams/003_naive_llm_three_findings.png`): the agent asks the command as well as its manual; many test command lines v1's generator writes do no work; the agent is inventive but a poor judge of its own work. Section 4 (added in 0.4), `cut` and `sort` (runs 7 and 9), the first commands with no example to copy: unprompted, the agent ran the paper's split-and-join test for `cut` and wrote and tested a merge for `sort` (the aggregator step the paper leaves out of scope); its PaSh tables match PaSh's own hand-written ones; loaded into PaSh's real code, the `sort` merge class gives no answer for ordinary sorts (PaSh rejects round robin with a custom merge and hides the error); through v1's generator, `=` on short options (a convention in v1's own `uniq` reference) leaves the agent's `cut` grammar and v1's model output with 0 working command lines at 4 options, against 360 for v1's reference; v1's committed `sort` annotation (`stateless`) predates the 2025-12 line-order check. Suggests a pre-tracing run of each generated line, `=` only on long spellings, checking adapter output in the consumer's code, and a model-written aggregator checked by v1's split runs. Section 3 (added in 0.3), `convert`, the command the paper's cost section singles out, from run 8: the agent learned the interface from the program (manual vs `-help` vs library strings, 261 accepted options), finding a manual misspelling and a flag-or-value error that both of v1's `convert` grammars copy; v1's grammar language can hold options between files (v1's own PaSh test grammar does), but the reference, model and agent grammars use two positions, and through v1's generator at one option per line only 4 of the agent's 2,422 distinct lines (and 0 of the reference's) have an input and an output; PaSh's parser stops at the first file, so options after the input reach the annotation as file names. Suggests widening the binary check, using positions for interleaved options, testing options singly before combining, and recording which option orders an annotation holds for. Section 2 (added in 0.2), a command beyond the core utilities, from run 6 (`binwalk`): the installed binary is a Python script and the agent took the syntax from its source; the manual lags the program (49 options vs 51); binwalk finds nothing in seven of v1's eight content files; a correct integer range in the agent's grammar becomes 65,536 runs in v1's generator; `-D` runs commands, which v1's grammars would type `Command`. Suggests format-bearing content, sampled ranges, `Command` typing, and stating per command whether it was treated as opaque. Section 1 as in 0.1: Proposals for the resubmission drawn from the naive-LLM runs, collected under one heading. Section 1, two case studies framed as extensions of v1: (A) the agent asked the binary as well as the manual and found six syntax facts v1's reference files do not record, two of them stated in the manual and four only in the binary (one via `rm`'s own error message); (B) `grep`'s `-e`/`-f` form, absent from all three of v1's `grep` grammars and invisible to the reference comparison, which the agent wrote into its grammar after reconciling PaSh's hand-written annotation with the binary. Suggests a syntax check against the binary in v1's existing sandbox, and scoring against two yardsticks. PDF beside it. |
| [`syntax_files_vs_v1.md`](../../naive_llm_caruca/syntax_files_vs_v1.md) | **Version 0.1, 26 October 2026, draft.** The agent's syntax files for `rm`, `cut`, `sort` and `convert` (runs 5, 7, 9, 8) against v1's reference and v1's model output, every difference checked on the installed programs, and all three fed to the four v1 programs that read a syntax file. The files mostly agree on what the options are (read by GNU's rules, all three read every valid real-world `cut` and `rm` line; v1's model output misses 831 of 5,010 `sort` lines for lack of `-k`), and where they differ the agent's is usually closer to the program. Which is "better" depends on the reader: v1's matcher reports the reference as reading nearly every `cut` and `sort` line, but checked word by word only 78 of 5,856 `cut` and 2,360 of 5,010 `sort` readings are right (agent: 2,522 and 4,455), and corpus-wide 267,070 of 665,631 lines count as read only by taking a word as an option it is not; v1's generator favours the reference (`=` on short spellings, empty choices and an optional `rm` file cost the agent); the ShellCheck adapter gets a useful `convert` warning only from v1's model output; v1's scorer misses 7 of 8 planted single-attribute changes. Scripts and results in `naive_llm_caruca/comparisons/2026-10-26_syntax_files_vs_v1/`. |

## findings/

**Archived 13 October 2026.** At Tiran's direction the twelve finding files, every run under
`eval/runs/` and `eval/v1_runs/`, the metrics database, the campaign ledgers and the parity
drill-downs were moved — not deleted — to `eval/_archive/2026-10-13_parity/` (its README lists
each). The folder below is empty until task 014's runs produce new findings; the archived ones
remain citable and the console can read them with `CARUCA_EVAL_ROOT` pointed at the archive.

Since 22 September 2026, each conclusion this project reaches also lives as its own file in
[`findings/`](findings/) — one claim per file, with the numbers behind it, what each is counted
over, the campaign or runs it came from, and any correction it has been through.

The point is that they can be re-checked. The execution console recomputes each number with
today's scorer and reports whether it still holds, which the prose documents above cannot do.
Eleven were backfilled from `v1_v2_parity_study.md`, `e0_artifact_pinning.md` and
`memory/caruca_v1_stage1_baseline.md`; the documents remain the place the reasoning is written
out at length.
