## Summary

Tools that parallelize, distribute or check shell scripts (PaSh, POSH, ShellCheck, Shseer) need a hand-written description of every command they meet: what it reads and writes, whether its work can be split, and what must be true of the filesystem before and after it runs. The paper presents Caruca, which produces these descriptions automatically for commands whose source code is unavailable. A large language model (GPT-4o, prompted with three worked examples) turns the command's manual page into a "syntax specification", a small typed grammar of its flags, options and arguments (§3). Hand-written code then enumerates command lines from that grammar, limited to four flags on the strength of a usage study of 49K GitHub shell scripts, and pairs each with filesystem states from a small model (file, directory, missing, missing parent) and with sample file contents (§4). Each pair runs in an overlay-filesystem sandbox while system calls are recorded (§5). Rules turn the recordings into properties: a parallelizability class, input and output files, whether arguments can be split, whether output is smaller than input, dependence on the current directory, and filesystem pre- and post-conditions (§6). Adapters emit the four tools' formats.

The evaluation (§7) asks four questions over 120 commands. Generated specifications match the tools' own hand-written ones for 59 of 60 commands (Tab. 1: PaSh 52/52, POSH 16/17, ShellCheck 6/6, Shseer 18/18), with `git` the one failure. The model's syntax specifications match a hand-made reference exactly for 116 of 120 commands. Generated command lines cover 651,733 of 666,468 real invocations (97.78%) once flag order, path names, integers, strings and argument counts are normalized. With a two-flag limit, 103 commands finish within an hour and all but `convert` within a day. The paper claims the first fully automated, generally applicable specification miner for opaque components.

## Strengths

- **S1.** The language model is confined to the one step where its errors can be measured: "The LLM solely generates the syntax specification—it is not involved in any remaining components" (§2.2). Every behavioural property comes from an observed execution, and the paper builds a 120-command hand reference (two annotators, 80 person-hours, 16 disagreements reconciled, §7.2) to measure the model's step on its own.
- **S2.** One intermediate specification serves four independent consumers with different formats (§6.4, Tab. 1), and two of them are re-run for real: ShellCheck's suite of "over 2.2K tests" passes with the generated checks (34 of those tests exercise them), and PaSh's benchmark suite gives identical output, "confirmed by hash comparison" (§7.1).
- **S3.** It automates what the main consumer's own paper judged out of reach. PaSh states that "Automating such an analysis is infeasible, as individual commands are black boxes" [arXiv:2007.09436, §2.2]. Caruca also reports errors in the hand-written references it is compared with (`grep -c` is not stateless; `ps` and `cp` are misclassified, §7.1).
- **S4.** Design choices are tied to data. The flag limit comes from counts over 665K real invocations (§4.1), and the coverage study separates the contribution of each normalization (Fig. 6) and says where one is unsafe: "this is not a valid normalization for commands whose semantics depend heavily on the input argument content" (§7.3).
- **S5.** Cost is reported including the unfavourable cases: Fig. 7 shows which commands did not finish in five hours, and §7.4 names the 24 commands that need more than a day at the default limit and the `convert` outlier.

## Weaknesses

- **W1 (major).** The headline numbers come from different, partly unstated settings, so no single setting is shown to be both accurate and affordable: the introduction's "within 1 hour for 103 out of 120 commands" is the two-flag limit, the default is four (where Fig. 7 projects 8.3 days for `grep`, 16.5 for `sort`, 123.7 for `test`), and §7.1 and §7.3 never say which limit produced their results. Fix: state the setting behind every number and report accuracy and coverage at the two-flag limit.
- **W2 (major).** Correctness is checked only where a hand-written specification already exists ("we compare Caruca's generated specifications for those invocations only", §7.1), so the part that is Caruca's added value, the "thousands of command invocations absent from the built-in ground-truth specifications", has no accuracy figure. Fix: sample those invocations and validate them independently.
- **W3 (major).** "Stateless" and the other properties are general claims inferred from a finite number of test runs (§6.3), with no description of how test inputs and split points are chosen and no measured error rate, although the paper itself says a wrong label "could lead to incorrect results" (§7.1). Fix: describe the sampling and measure how often a "stateless" label fails on inputs built to break it.
- **W4 (major).** There is no baseline and no ablation, so each component's necessity is asserted: no language model asked directly for the final specification, no non-model syntax extractor (Explainshell [27] is dismissed in §8 without a measurement), no second model, no repeated run, no token cost. Comparable work reports a model comparison, a single-prompt variant and its token cost [arXiv:2401.00563].
- **W5 (major).** Several top-level claims exceed the evidence: "completely eliminating manual effort" beside checks "which we manually insert into Shellcheck's source" and aggregators that are "out of scope"; "immediately usable by existing systems" beside "For POSH, as we were unable to run it"; ShellCheck "6/6 (100%)" after 41 of its 47 command-specific checks were set aside; and PaSh output equality with no speedup reported. Fix: scope the claims or add the missing measurements.
- **W6 (major).** The 97.78% coverage figure has an unclear denominator and rests mostly on the weakest normalizations: Fig. 4's forty most frequent commands include `rmdir` and `realpath` below 1,000 uses but not `git`, `grep`, `sed` or `curl`, so the corpus appears filtered in a way the paper does not state, and 493,632 of the 651,733 matches in Fig. 6 depend on string or argument-count normalization. Fix: state the filter, and report per-command coverage and a conservative figure.
- **W7 (minor).** Related work omits the closest lines: black-box inference of parallelization facts for the same consumers [arXiv:2012.15443], model-written interface specifications with a repair loop [arXiv:2401.00563], and documentation-only exploration of command options by a language model [arXiv:2409.00922]. The "first" claim needs scoping against them.

## Detailed Comments

### Novelty and relation to prior work

No retrieved paper does substantially the same thing: deriving behavioural specifications for several consumers, for commands without source, from documentation plus traced execution. Each stage, however, has a clear precedent that the paper does not discuss.

- **PaSh [arXiv:2007.09436]** (cited as [43]) defines the classes and the format Caruca targets and calls automation "infeasible", so Caruca's delta is real: per-flag inference of class and inputs/outputs with no human in the loop. Two points from that paper bear on Caruca's framing. First, PaSh reports its annotations were "used to annotate 47 commands, totaling 708 lines of JSON—an effort that took about 3–4 hours" (§3.2). Caruca calls the same task "manual, laborious, and error-prone" (abstract), yet needs more than an hour of machine time for 17 of 120 commands even at two flags (§7.4). The case for Caruca therefore rests on completeness and correctness per flag combination, not on authoring time, which is exactly the part W2 finds unevaluated. Second, PaSh keeps parallelizable-pure and non-parallelizable-pure apart because only the former, with an aggregator, is parallelized; Caruca's 52/52 counts the two as one answer (§7.1).
- **KumQuat [arXiv:2012.15443]** is not cited, although it shares an author with this paper. It runs commands as black boxes on generated inputs and synthesizes the combining step for 113 of 121 command and flag combinations in 39 to 331 seconds each. That is the piece Caruca declares "out of scope ... but covered in prior work [15–17]", where the paper cites loop-parallelization synthesis rather than the Unix-specific system. §8's "Unix Synthesis" paragraph contrasts Caruca with "automatically generating parallel or distributed versions of an existing command or pipeline" but cites only [3, 6], program synthesis from manual pages, neither of which does that. Caruca's delta over KumQuat: it enumerates the option space from documentation instead of taking invocations from scripts, and it infers file inputs/outputs and filesystem conditions. The two look complementary, and pairing them would address W5's aggregator gap.
- **KernelGPT [arXiv:2401.00563]** (January 2024) and **ProphetFuzz [arXiv:2409.00922]** (September 2024) show that the two halves of Caruca's first stage were established. In KernelGPT a language model writes an interface description (of system calls, from source), validator errors are fed back for repair, and an unmodified non-model fuzzer consumes the result. In ProphetFuzz a model reads documentation only ("with Only Documentation") and chooses option combinations to run for 52 command-line programs. §8 says Caruca differs from fuzzing work because it "leverages documentation to guide generation", which is not a difference from ProphetFuzz. Caruca's delta is the goal (behaviour specifications, not bugs) and the typed grammar reused for systematic enumeration. The claim to be "the first fully automated and generally applicable specification miner for opaque components" should be narrowed accordingly.
- **GUIde [arXiv:2510.01453]** is concurrent (posted two weeks earlier; no citation expected) and has the same first step: a model converts manual pages into a machine-readable grammar. It reports that "naïvely prompting LLMs produced unusable grammars with many errors", and measures the share of real invocations its grammars parse: 89.8% on average over 20 commands, with failures from flags missing in the manual page, very long pages, and `find`. Caruca reports 116/120 exact matches with a three-attempt loop. The results are not contradictory (different grammar targets, models and metrics), but they suggest a cheap extra check: the share of the 666K real invocations that Caruca's model-written grammars parse, which tests the syntax step against usage instead of against a reference written from the same manual page.

Also worth positioning against: model-based generation of program specifications from source [arXiv:2401.08807, arXiv:2404.00762]; mining constraints from API documentation and checking them against real responses [arXiv:2504.17287]; and inferring file dependencies from system-call traces [arXiv:1905.11070], a precedent for §6.3's input/output rule. CLIFuzzer [20], "mining grammars for command-line invocations", is cited only in a list of fuzzers although it produces the same kind of artefact as §3.

### Method and soundness

- **Finite tests, general labels (W3).** §6.3 labels an invocation stateless "if the output of invoking C_i is identical to concatenating the outputs" over line-split parts of an input. The paper does not say how many inputs or split points are tried, how they are chosen, or how disagreeing runs are merged into one class. An input with no adjacent duplicate lines, for example, cannot tell `uniq` from `cat`. KumQuat [arXiv:2012.15443] picks inputs by how many wrong candidates they eliminate and still calls its results only "plausible". The limitations paragraph (§2.2) treats finiteness as a risk of incompleteness, not of wrong labels.
- **Arguments that are programs.** The paper notes string normalization fails for `xargs` and `nohup` (§7.3). The same holds for `sed`, which is in the suite (Fig. 7): KumQuat's result tables give plain concatenation for `sed` with a substitution script, a re-run step for `sed 100q`, and "No combiners g exist" for `sed 1d`, so the class depends on the content of the string argument.
- **The side-effect rule and the example disagree.** §6.3 defines side-effects as "writes to a path not named in its arguments", yet §6.1 lists `rm` as side-effectful and Fig. 3 gives `rm` the side-effectful class although it changes only its named argument. §7.1 says `cp` should be "pure", which does follow the rule. The rule that separates `rm` from `cp` is not given.
- **Rules without guards.** Fig. 3 marks `rm` as both having no outputs, "O({})", and as shrinking its input (↓). The output-smaller-than-input rule (§6.3) quantifies over all output files, so it holds trivially when there are none.
- **Current-directory dependence** is detected by the presence of `getcwd` in the trace (§6.3), while §6.1 names `ls` as the example. *Unverified impression:* a command can read the current directory without asking for its name, so the rule may miss the paper's own example.
- **No check of the grammar against the binary.** Validation only loads the model's output as Python and type-checks it (§3.2). The tracing stage already sees usage errors and exit codes, which could flag missing or spurious options, as the repair loop in KernelGPT does with its validators.
- **State outside the model.** `kill`, `date`, `timeout`, `who`, `df` and `chroot` appear in Fig. 7. The paper does not say what specification is derived for commands whose behaviour depends on processes, time or privileges rather than on files.

### Experiments and evidence

- **Settings (W1).** About thirty commands in Fig. 7 have projected rather than measured bars at four flags, among them `test`, one of the two most-invoked commands in the corpus (Fig. 4), and `grep`, `sort`, `sed`, `uniq`, `tail`, `mv` and `ls`. §7.3 says of exact matches that "Caruca executed the exact same invocation during its exploration"; for these commands that exploration did not complete, so coverage seems to be computed over generated command lines, not executed ones. §7.4 mixes measured and projected results in one sentence ("successfully generates specifications for 80 commands within an hour and 96 within a day").
- **Which grammars fed Tab. 1?** §7.2 reports that the model's grammar for `sort` lacks the sorting-key option and two others, and `sort` runs through PaSh's benchmark scripts ("all scripts that contain sort ... are capped at 8×" [arXiv:2007.09436]), yet PaSh is 52/52. If Tab. 1 used hand-corrected grammars, end-to-end accuracy without manual effort was not measured. If it used the model's, the paper should show why such errors did not matter. The "99.7% of all flags, options, and arguments" and "mistakes being non-catastrophic" in §2.2 have no visible denominator or test in §7.2.
- **Independence.** The comparisons in §7.1 are manual, with no stated criteria, and the authors overlap with those of PaSh [26] and Shseer [29]. A scripted comparison, or one by people outside the group, would carry more weight.
- **Held-out commands.** The grammar's types were designed by studying "the documentation of 120 command[s]" (§3.1), apparently the same 120 used for evaluation. The three worked examples in the prompt, `rm`, `mv` and `touch` (§3.2), are also evaluated commands (Fig. 7), so three of the 116 matches had their answer in the prompt. The manual pages are of widely published GNU and POSIX tools that the model has likely seen. For "opaque components" the relevant test is a command the model has not seen.
- **Coverage arithmetic (W6).** §7.3's text and Fig. 6 disagree. The text says flag normalization "pushes this to a total of 64,542 matches", fewer than the 66,882 exact matches it starts from, then 122,816 (18%) with paths and integers and 632,780 (94%) with strings. Fig. 6 gives 158,101 (23.7%) and 500,007 (75.0%) at the same points. The two accounts attribute 18,953 versus 151,726 matches to argument-count normalization. From Fig. 6, coverage without string and argument-count normalization is 23.7%, and 59.1% if strings are allowed only for the printing and filtering commands (236,048). The defensible range is therefore roughly 24% to 98%, and the paper bolds the top.
- **PaSh benefit.** PaSh parallelizes a pure command "by encoding it as a group of (parallel) map functions followed by an aggregate that merges the results", says the other pure class "cannot be parallelized within a single data stream", and reports speedups that start at 0.89× [arXiv:2007.09436]. Identical hashes therefore cannot show that Caruca's annotations preserve PaSh's benefit, which §7.1 itself lists as a failure mode ("missing an optimization opportunity"). Report parallelized stages and speedup under both sets of annotations.
- **Missing ablations.** Accuracy as a function of the flag limit; typed versus untyped argument generation (§2.1 asserts that arbitrary strings are "extremely unlikely to lead to valid executions"); and behaviour-aware pruning, which the `convert` discussion ("exhaustive flag combinations exaggerate its complexity") invites.

### Clarity and presentation

The paper is well organized, with a running `rm` example and a clear mapping from challenges to components. Three things hinder a reader: the labels C1 to C4 name both the challenges (§2.1) and the components (§2.2); Tab. 1 puts commands, checks and specifications under one "Correct" column; and the 120 commands are never listed (Fig. 7 names 79). Nits: "88 specification ground truths" sums to 87 as listed and to 93 with Tab. 1's 18 for Shseer; §4.1's flag counts sum to 665,614, not 666,468; "Ubuntu 22.07"; "the LLM Parser (Q3)" should read Q2.

## Questions for Authors

1. Which flag limit and time limit produced the specifications in Tab. 1 and the generated set used for coverage, and were those runs complete for `grep`, `sort` and `test`, which Fig. 7 shows unfinished at five hours?
2. Did Tab. 1 use the model-written syntax specifications or the hand-made reference ones? If the former, how did `sort` pass with its sorting-key option missing?
3. How was the 666,468-invocation corpus selected from the 49K scripts, and what share of all command invocations in those scripts does it represent?
4. For the stateless test, how many inputs and split points are tried per invocation, from which content, and how are disagreeing runs merged? Has a class ever changed when inputs were added?
5. With Caruca's annotations in place of PaSh's own, how many pipeline stages does PaSh parallelize, and with what speedup?
6. How does the syntax step do on a command unlikely to be in the model's training data, and how much do results vary across repeated runs and across models?

By dimension: the idea and the system are above the usual bar. Nothing retrieved builds specifications for four consumers from documentation and traced runs, and PaSh's own paper called the task infeasible to automate. The core result holds within its scope: for the invocations the consumers' benchmarks exercise, generated specifications agree with hand-written ones. What pulls the assessment down is the experimental design (no baseline, no ablation, one model run once, and accuracy, coverage and cost reported at settings that are not shown to coincide) and the positioning (the nearest prior systems are absent and the "first" and "eliminating manual effort" claims are broader than the evidence). The most valuable additions would be one table giving accuracy, coverage and cost at the same flag limit; an independent check of specifications outside the hand-written references; and a baseline in which a language model writes the final specification directly.

It uses default weights and a rescale fitted on 14 papers, with roughly ±1.5 points of uncertainty.
