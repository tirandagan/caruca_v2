Caruca v2 · Task 022 · Run 19 November 2026

Caruca's annotations and the naive LLM's, run under PaSh

PaSh speeds up a shell script by running several copies of a command at once on pieces of its input. It decides what is safe from a few annotation files per command. This test gave PaSh two generated sets of those files, one from Caruca and one from the naive LLM, ran the same command lines under each, and compared every result with plain bash.

The short answer

PaSh is running, and it reads the files it is given. Every check passes before and after the batch, and in none of the 2,377 runs did PaSh split a command whose loaded files forbid it.

139of139splits allowed by Caruca's files that PaSh carried out

Caruca's files are used every time, and they allow few splits

They allow a split in 139 of the 605 runs made with them. The files generated from Caruca's PaSh grammar gave the right output in all 382 runs. The files generated from its main grammar gave a wrong output on 7 sort lines.

423of655splits allowed by the naive LLM's files that PaSh carried out

The naive LLM's files allow far more

They allow a split in 655 of 1,013 runs. All 423 splits PaSh carried out gave the right output. In 19 further runs, all grep, PaSh returned nothing and reported success. PaSh's own hand-written grep files do the same.

329of2,377runs in which PaSh's compiler failed

PaSh is the largest single source of lost splits

In these runs PaSh's compiler stopped with an error and the script ran as plain bash: right output, nothing parallel. That took 186 of the 655 splits the naive LLM's files allow, 63 of the 178 that PaSh's own files allow, and none of Caruca's 139.

6.4×faster than bash with Caruca's files, on a grep that works hard on every line

Where splitting pays, every set that allows it gains about the same

6.4 times with Caruca's files, 6.1 to 6.3 times with the naive LLM's and with PaSh's own. The benchmark lines themselves are too cheap to gain: 11 of the 12 lines timed were slower when split.

46of46whole benchmark scripts whose output matched bash, under every set

On whole scripts every set is correct, and they differ in how many PaSh splits

PaSh split 35 scripts with the naive LLM's set, 35 with its own, 35 with Caruca's main-grammar set and 27 with Caruca's PaSh-grammar set.

What was compared

An annotation is three files per command: a table of the command's options, a description of what it reads and writes, and a description of whether its input may be cut into pieces and how the pieces' outputs are joined again. The command lines

382 lines for cat, cut, grep, sort, rm, cp, wc and split. 220 come from PaSh's own benchmark scripts. 141 were picked because the sides give PaSh different answers. 21 are cases the earlier file-by-file comparison had flagged.

How a run was judged

Each line ran once in plain bash and once under PaSh with 8 workers, on the same 4 MB text. Output, exit status and files left behind were compared. A run counts as split only when two signals agree: PaSh's own log, and a stand-in for the command that counts how many copies of it started.

State of a runWhat it means
SplitPaSh ran several copies of the command on pieces of the input and joined the results.
Split set up, no data arrivedPaSh built a split with 8 workers on a stream that carried nothing, so no copy ever started. The output is empty.
PaSh's compiler failedPaSh raised an internal error and ran the script as plain bash. The output is right and nothing is parallel. At most PaSh prints a general warning that nothing was parallelized; the error itself appears only in its debug log.
Not splitPaSh ran one copy, with no error.

Where the output went wrong

Every run whose output differed from bash was repeated by hand: cut the input into pieces, run the command on each piece, join the results. If the hand-made split is wrong too, the cause is the annotation and not PaSh.

SideWrong outputsWhat happened
Caruca, PaSh grammar0 of 382Nothing.
Caruca, main grammar7 of 223Seven sort lines that add a second option to a sort order: -n -u, -n -s, -g -u, -h -s, -k 1 -u, -k 1 -s, -k 1,1 -u. The files say the sorted pieces can be joined end to end. PaSh did that, and the result is not sorted. The hand-made split is wrong as well, so the cause is the annotation. Of the 8 sort lines these files let PaSh split, sort -m alone came out right.
Naive LLM, all runs19 of 1,013All grep, in two of its three runs (11 and 8). Searching a folder with -r: the files describe the folder as a stream of input, PaSh splits it, no data arrives and the output is empty. With --color: the option table says the option takes the next word, so the search pattern is swallowed. The earliest grep run has neither fault.
PaSh's own16 of 377The same two grep faults (11 runs). grep -m and grep -A split (2). cut -z split (2). sort --help printed once per worker (1).
No annotation0 of 382Nothing.
  • Four of those seven sort lines are split correctly by all four of the naive LLM's runs (-n -u, -n -s, -g -u, -h -s), and the other three by one run. Its files tell PaSh to merge the sorted pieces with sort -m. Caruca's method chooses between "join end to end" and "do not split", as the paper notes, so a merge step is outside what it can say today. PaSh's own files do not split any of the seven.
  • The naive LLM's two grep faults are also in PaSh's own grep files, which it had been shown as an example. Its earliest grep run has neither fault and allows very little: PaSh split 1 of its 48 lines.

PaSh's own failures

In 329 of 2,377 runs PaSh's compiler raised an internal error. The script then ran as plain bash, with the right output and exit status 0. When no part of a script was parallelized, PaSh prints a general warning that suggests checking the annotations, the same warning it prints when a script has nothing to parallelize. The error itself appears only in the debug log.

The benchmark lines are too cheap to gain from a split. On a 64 MB input, cut took 0.15 s in bash and 0.23 s under PaSh, split or not. Of the 12 lines timed, 11 were slower split than in bash, and one, sort -rn, was 1.17 times faster. 54 combinations of line and side were timed, 5 runs each, and every output was right.

What this suggests

Interpretation

The points below are a reading of the numbers above. They are not measurements.

  • Caruca's files are the careful ones. What Caruca saw in a trace, PaSh could use, every time. The cost is reach: a different option, a file argument or a value written against its option, and there is no answer.
  • Caruca's one unsafe answer has a clear shape. It is sort with a second option that changes which lines count as equal. The earlier reading of the files predicted it. Here it is confirmed under PaSh on 7 lines.
  • The naive LLM's files reach as far as PaSh's hand-written ones, and carry two of the same faults. Its sort files show one thing a generated annotation can add to Caruca's two outcomes: a merge step.
  • Much of what limits both sets is PaSh. Its compiler failed on 15 of the 46 cut benchmark lines, with the naive LLM's files and with its own alike.

Limits and corrections

Limits

  • Eight commands and 382 lines. 162 of the lines were chosen because the sides differ, so pooled counts overstate how often they differ. The benchmark-line table is the unbiased part.
  • One input text. A wrong split shows only on input that exercises it, so a line that came out right here is not proved safe.
  • In the lines picked for disagreement, file names were replaced with prepared files. Options are unchanged.
  • Whole scripts read this test's text, not their own data, so nothing is said about their speed.
  • Timings were taken with the laptop on battery power.
  • One PaSh revision and one worker count (8).
  • 3 of the selected lines could not be run: two whose quoting the runner could not parse, one that uses command substitution.

Corrections made during the run

The first pass exposed three faults in the test harness. Each was found from a run in the "unknown" state or from a failed check, then fixed, and the whole pass was run again from scratch. The first pass is kept.

  • Worker copies handed a pipe as their file argument were counted as PaSh's housekeeping. 65 runs were marked unknown; 35 became "split".
  • For cat lines the input was fed with cat, which the side's own cat files also governed. Those lines are now fed another way.
  • The bash reference ran the real program while the PaSh run used the counting stand-in, and --help prints the program's name. The reference now uses the stand-in too.

The 30 runs still unknown after the first fix were real behaviour and became the state "split set up, no data arrived".
